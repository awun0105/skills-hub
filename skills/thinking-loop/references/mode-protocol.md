# Operator fallback and handoff

Use this file when peer skills cannot be loaded or a compact handoff is useful.
This supplies core behavior without requiring six installed peers. It cannot
ensure identical output quality in different hosts or models. Only the current
owner chooses the next operation; do not create recursive controllers.

## Fallback operators
| Operator | Minimal operation | Exit artifact |
| --- | --- | --- |
| Top-down | Define deliverable and acceptance; ground/map parts and dependencies; flag assumptions; recompose interfaces and end-to-end checks. | Testable map or plan, integration risks. |
| Bottom-up | Inspect a specific observation/source and its conditions; compare cases where useful; discriminate uncertain explanations; bound the claim. Do not manufacture alternatives for a demonstrated cause. | Scoped explanation/evidence gap, provenance. |
| Divergent | Vary mechanisms within confirmed constraints; honor requested count without padding; label speculation. If only ideas are requested, deliver without ranking. | Distinct candidates with assumptions/discriminators. |
| Convergent | Filter confirmed constraint violations; distinguish unknown feasibility; compare grounded criteria; test sensitive assumptions; choose, trial, or report no valid choice. | Conditional or supported recommendation, not authorization. |
| Shallow | Apply the selected operation lightly; retain necessary checks; allow multiple provisional options under divergent breadth; escalate material uncertainty. | Minimum adequate local result. |
| Deep | Strengthen verification of the selected operation; inspect load-bearing dependencies, counterexamples, and sensitivity; gather missing evidence rather than repeatedly speculate. | Supported conclusion and explicit limits. |

A skill instruction does not configure model reasoning-effort or grant tools.
A narrow high-stakes triage can precede rigorous diagnosis but cannot certify an
unverified destructive action. Follow host approvals and specialized workflows.

## Minimal handoff
Transfer only what the next operation needs, using ordinary prose or structured
fields when the host benefits. This is a task record, not a private scratchpad.

| Field | Meaning |
| --- | --- |
| deliverable / remaining criteria | User-requested outcome and unfinished obligations. |
| evidence | Claim, inspected source or user report, relevant version/conditions. |
| evidence status | observed, reported, inferred, assumed, or unknown. |
| candidates / constraints | Retain only if an actual comparison or idea task needs them. |
| result / artifacts | Produced output and which checks actually ran. |
| unresolved question | The specific uncertainty that matters to the next decision. |
| proposed action | One useful permitted check or operation, with expected discriminator. |
| completion | completed, conditional, or blocked relative to the requested scope. |

Omit unused fields and avoid numeric confidence without calibration. Do not infer
independent corroboration from repeated copies of one report. Recheck results when
source versions, inputs, environments, or patches invalidate their relevance.

## Stops and handoffs
Return to the current owner; do not call peer skills recursively. Stop after an
ideas-only deliverable instead of forcing a choice. Stop after a supported choice
instead of inventing further candidates. When a check is unavailable, name it as
unperformed and explain its consequence; never mark it passed.
